# 蛋仔地图开发公共规则

本区块由蛋仔 Agent 技能包安装器维护。它只提供跨项目的硬约束；原点版与世界版的专属规则由地图自己的 `AGENTS.md`（代理规则文件）补充。受管区块之外的用户内容不由安装器覆盖。

> 公共技能按任务域安装，不代表每个会话都要读完整技能包。必须用代理打开总工作区；只打开地图子目录时，先提醒用户重新打开总工作区并新建会话。

## 动手前的硬门槛

1. 先确认本轮实际要修改的文件、目标地图、原点版或世界版、单人或多人，以及用户要保留的效果；无法确认就先问，不带着疑惑写代码。
2. 写或修改任何接口调用前，必须确认接口确实存在，并核对完整签名、参数数量、顺序、类型、返回值、默认行为、调用对象、运行侧和前置条件。至少查当前工程定义、本地对应版本官方手册和官方案例；三者不能互相印证时停止猜测。
3. 接口研究只能证明“找到线索”，不能代替阅读命中上下文。不要为了让报错消失而连续乱换参数、换接口或加兜底；先说明证据和未知项。
4. 用户没有要求时，不启动编辑器、不开始试玩、不操作场景、不调用外部模型。需要真实验证时先说明最小验证范围。
5. 看到报错先用中文说明现象、原因和影响，等待用户确认后再修；用户明确要求直接修复时才可跳过等待。解释原因时不要堆代码或接口名。

## 修改边界与外部契约

6. `Data/`、`data/`、接口定义文件、官方配置、`.codemaker/`、`.vscode/` 和官方生成目录只读，不能写入自定义代码，也不能把它们当成稳定用户文件。
7. 同步到地图的 Lua（脚本）文件名不得使用中文；功能代码按职责放自建模块，入口文件只做必要加载和初始化，并留意入口引用上限。
8. 删除、改名、移动、合并、拆分函数或文件前，先做导出契约扫描。被蛋码、编辑器、ECA（编辑器事件动作）或其他外部调用的函数，名称、路径、注解、参数顺序、类型和返回值未经用户确认不得改变；无必要不要把中文名和英文名互换。
9. 有准确的单位实例编号、预设编号或 UI（界面）节点编号时优先使用已确认编号；没有编号才按名称查询。新取得的正式资产及用途写入唯一资产清单。
10. 任何批量修改都必须先确认并记录现有 Git `HEAD`（当前提交）和已有差异；这已经是代码、文档和规则的恢复依据，不得为普通批量修改额外复制文件、创建备份分支或重复提交。只有 Git 无法完整恢复的场景/UI（界面）/预设状态，或用户明确要求时，才为本批目标建立一次范围快照。仍须先做小范围试点、排除官方文件和他人改动，并逐文件审查差异；同一批次复用同一恢复依据，做不到就逐个修改。

## 测试、性能与日志

11. 测试的目的是真正打通当前开发卡点，不是为了凑测试记录。优先最小代码片段和最短玩家路径；测试中加入中文诊断日志并标记 `【测试专用】`，观察到足够证据后立即退出测试模式，移除或明确清理测试代码。
12. 统一记录日志等级：正常过程用 `GlobalAPI.debug()`（调试）；可恢复的异常或输入问题用 `GlobalAPI.warning()`（警告）；已经导致功能失败用 `GlobalAPI.error()`（错误）。日志优先中文，不能把普通进度写成警告或错误。
13. 地图在沙箱中运行。避免无界表、重复计时器、逐帧全场扫描和高频无意义日志；涉及运动器优先确认世界空间与本地坐标的差异。世界版还要按服务器内存和服务端/客户端职责控制对象数量。
14. 每次代码修改后都要反查逻辑、接口、日志、注释、文件边界和原有功能；静态检查通过不等于玩法完成。

## 文档与沟通

15. 每张地图只维护一份玩法需求、开发计划、资产清单、项目 README（项目总览）和开发日志。开发计划先逐字记录会影响玩法、效果、验收或修改原因的用户原话，再写代理理解；用户未确认完成不得标记完成。
16. 新增或修改的函数必须写清用途、输入、输出、副作用、失败条件、顺序依赖和清理时机。复杂代码注释要足够让下一位代理独立理解；用户明确说明的修改原因才写成原因注释，完整历史写开发日志。
17. 发现可跨地图复用的接口关系、编辑器边界、数值上限或高代价错误经验时，在本批次收尾沉淀一次。未验证内容只能标为待查证，不能写成公共事实。
18. 地图项目使用独立 Git（版本记录）仓库；动工前记录当前提交和已有改动，不丢弃用户或其他代理的修改。检查恢复依据不等于新建提交，只有形成实际交付批次时才提交一次。

## 跨地图协调边界

普通单地图开发、辅助工具开发和资料处理不得进入 `蛋仔工程\蛋仔地图施工协调层\` 的 Spec Kitty（规格任务治理）任务流、工作树或备份分支。只有用户明确要求跨地图协调时才使用该项目；已有历史分支不自动清理。
