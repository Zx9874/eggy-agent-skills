# 蛋仔UGC编辑器插件开发教程

## 总览

### 是什么

蛋仔UGC插件系统是嵌入《蛋仔派对》编辑器的**可扩展工具宿主框架**。它在 PyQt5 的 QtWebEngine（Chrome 77 内核）中加载 H5 页面作为插件界面，通过 Qt WebChannel 桥接前端 JavaScript 与后端 Python / 引擎 API，使开发者能够用标准 Web 技术构建可深度集成到编辑器的功能模块。

可以这样直观理解：把编辑器看作一个浏览器，插件系统就是它的"扩展商店"——每个插件是一个独立的前端页面，通过统一桥接协议调用编辑器底层能力。开发体验与浏览器扩展或 Electron 应用中的 WebView 通信模式高度相似：写 HTML/CSS/JS 界面，通过注入的桥接对象调用原生能力，回调接收结果。

在架构层级上，它位于编辑器宿主进程与工作室自研工具之间，扮演"标准化胶水层"的角色：屏蔽帧同步与状态同步两种引擎的差异，向插件开发者暴露统一接口。

### 有什么用

插件系统解决的核心问题是**编辑器扩展能力的碎片化**。在此之前，工具开发者向编辑器注入自定义功能，要么深入修改编辑器源码，要么用临时脚本绕过，缺乏隔离性和可维护性。插件系统通过以下关键能力改变这一局面：

* **界面完全可定制**：前端为标准 H5，符合 Chrome 77 规范即可，CSS/JS 自由发挥，无需学习 Qt 控件体系
* **统一 API 入口**：一套 `runEditorAPI` 调用，底层自动适配帧同步与 SE 两种编辑器模式，开发者无需感知运行模式差异
* **零前端初始化负担**：WebChannel 由框架自动注入，无需手动引入 `qwebchannel.js` 或调用 `new QWebChannel(...)`
* **Lua 扩展通道**：通过 `runLuaScript` 可执行任意编辑器 Lua 脚本，覆盖 EditorAPI 未暴露的扩展场景
* **自动类型桥接**：前端只需传 JS 基础类型，后端按 API 定义的参数描述（EdAPIDef）自动转换为目标 Python / 引擎类型
* **多页面导航**：通过 `navigateTo` + `listHtmlFiles` 可在单插件内组织多页面，支持向导式、多步骤复杂交互
* **统一错误协议**：所有结构化接口返回 `{success, result|error}`，前端可做确定性分支判断
* **声明式注册与热插拔**：编辑器按目录扫描 `config.json`，新增或移除插件不触动编辑器本体代码，无需重启

### 价值

**对工作室**：将编辑器能力的迭代周期从"等客户端版本"压缩为"前端页面级交付"。一个新工具的实现从需要修改编辑器 C++/Python 源码、走完整测试-打包-发布流程，缩短为一份 `config.json` + 一个 `index.html`。多个工具团队可并行交付，互不干扰；插件作为独立资产沉淀，升级或废弃单个工具不再触发编辑器主版本变更。Chrome 77 基线锁定带来运行时行为一致性，跨环境调试成本明显下降。

**对插件开发者**：开发门槛显著降低。熟悉 H5 开发的工程师不需要了解 PyQt 或编辑器内部机制，从零到第一个跑通的插件最短约 10 分钟。统一的回调签名与错误协议让故障定位时间显著缩短；示例插件（`sample` 目录）覆盖了主要 API 调用和页面导航场景，可直接对照验证；底层双模式适配让"一份代码 / 双端通用"成为默认状态。

**对 UGC 生态**：插件系统本质上是创作者生产力的放大器。当批量生成地形、一键排列关卡元素、自动检索资产库等高级操作被封装为插件在工作室内乃至社区流转，中腰部创作者无需理解底层 API 即可复现资深开发者的工作流。这种"知识工具化"的飞轮，是插件系统对 UGC 生态最深远的贡献：让创作力可复制、可积累、可传播。

## 一、架构设计

### 1.1 整体分层

插件系统在运行时形成自上而下严格分层的四层结构，每层职责单一、互不耦合。

```
┌──────────────────────────────────────────┐
│          表现层（H5 插件页面）            │
│   HTML 结构 + CSS 样式 + JS 交互逻辑     │
│   完全自由定制，无框架绑定                │
└────────────────┬─────────────────────────┘
                 │ Qt WebChannel 异步桥接
                 │ window.backend.*(args, callback)
┌────────────────▼─────────────────────────┐
│          通信层（WebChannel）             │
│   框架自动注入 qwebchannel.js            │
│   backendReady 事件驱动连接管理           │
└────────────────┬─────────────────────────┘
                 │ @pyqtSlot 方法调用
┌────────────────▼─────────────────────────┐
│       接口层（PluginInterface）           │
│   runEditorAPI / runLuaScript /          │
│   navigateTo / listHtmlFiles /           │
│   testConnection                         │
│   类型转换 + 返回值标准化 + 错误封装      │
└────────────────┬─────────────────────────┘
                 │ Editor API 路由
┌────────────────▼─────────────────────────┐
│          引擎层（编辑器内核）             │
│   ├─ 帧同步编辑器 Editor API             │
│   └─ SE 编辑器 Editor API                │
│   底层自动适配，对上层透明                │
└──────────────────────────────────────────┘
```

返回路径反向：引擎执行结果 → 接口层封装为 `{success, result|error}` → WebChannel 序列化 → 前端 callback。

### 1.2 核心技术栈

| 层级 | 技术 | 角色说明 |
| --- | --- | --- |
| 渲染容器 | PyQt5 v5.14.2 + QtWebEngine | 承载页面渲染，提供窗口管理。每个插件运行在独立的 `QWebEngineView` 中 |
| 浏览器内核 | Chrome 77.0.3865.129 | Web 内容解析与 JS 执行，对应 2019 年 9 月 Chrome 稳定版（Qt 5.14 内置） |
| 通信协议 | Qt WebChannel + qwebchannel.js | 基于 Qt 元对象系统的双向 JS 对象桥接；脚本由框架自动注入 |
| 前端技术 | HTML / CSS / JavaScript | 无框架强约束；原生 DOM、jQuery、Vue 2.x 均可使用 |
| 后端接口 | Python + `@pyqtSlot` | PyQt5 槽机制暴露方法，`result='QVariant'` 支持返回任意可序列化类型 |
| 脚本通道 | Lua | 编辑器内置 Lua 虚拟机，通过 `runLuaScript` 接口执行脚本文件 |

### 1.3 帧同步 / SE 双引擎适配

编辑器底层存在帧同步和状态同步（SE）两种运行模式，它们的 Editor API 在内部实现上有所差异——同样的"创建组件 / 查询单位 / 修改属性"在不同模式下调用的是不同的底层函数。插件系统的核心设计决策是把这一差异**完全封装在接口层内部**。

具体机制：`runEditorAPI(apiName, argList)` 接收调用请求 → 按当前编辑器运行模式查询对应的 API 定义表（EdAPIDef） → 执行参数类型转换（JS 基础类型 → 目标引擎类型） → 路由到帧同步或 SE 对应实现。

对开发者而言，`window.backend.runEditorAPI('create_obstacle', [...])` 在两种模式下写法完全一致，无需 `if (mode === 'frame_sync')` 之类的条件分支。一套代码、一份配置，双端通用。

### 1.4 通信模型与窗口模型

WebChannel 建立的是一条**进程内**的双向持久通道，不是 HTTP 或网络调用。三个关键特征：

* **自动注入**：DOM 加载完成后，框架向页面注入 `qwebchannel.js` 并完成连接初始化；前端代码无需引入或初始化
* **异步回调**：所有后端方法均为异步，无同步路径——这是 PyQt5 WebChannel 的固有约束
* **事件驱动**：前端通过 `document.addEventListener('backendReady', ...)` 获知桥接对象就绪

每个插件窗口由一个 `QWebEngineView` 实例承载，`config.json` 中的 `ui.is_docked` 决定是否嵌入编辑器主窗口（dock 模式），默认是独立浮动窗口。多个插件窗口可同时打开，各自持有独立的 `PluginInterface` 实例，彼此隔离。

## 二、版本与运行环境约束

### 2.1 运行时版本（硬约束）

| 组件 | 版本 |
| --- | --- |
| PyQt5 | v5.14.2 |
| QtWebEngine | 5.14.2 |
| 内嵌 Chrome 内核 | 77.0.3865.129 |

完整 User-Agent：

```
Mozilla/5.0 (Windows NT 6.2; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) QtWebEngine/5.14.2 Chrome/77.0.3865.129 Safari/537.36
```

此版本是硬约束——插件运行时不会升级内核版本。所有前端兼容性判断必须以 Chrome 77 为基准，**不能**以本机最新版 Chrome 调试通过作为达标依据。

### 2.2 Chrome 77 不可用特性速查

下表列出当前环境中**不可直接使用**的前端特性。开发阶段逐项对照，避免到集成环境才发现问题。

| 分类 | 不支持特性 | 常见影响场景 |
| --- | --- | --- |
| JS 语法 | 可选链 `?.`、空值合并 `??` | 深层属性访问、默认值 |
| JS API | `Promise.allSettled`、`globalThis`、`String.replaceAll`、`Array.at()`、`structuredClone` | 批量异步、全局引用、深拷贝 |
| HTML | `inert` 属性、`popover` 属性 | 禁用交互、原生弹层 |
| CSS | `gap`（Flex 布局）、`clamp()`、`:is()` / `:where()` / `:has()`、`aspect-ratio`、Container Queries、CSS Nesting、`@property` | 布局间距、动态尺寸、现代选择器 |
| Web API | FileSystem Access、Navigation API、Screen Wake Lock、Trusted Types | 文件读写、SPA 导航、屏幕常亮、XSS 防护 |

### 2.3 兼容性工程方案

1. **JS 语法降级**：使用 Babel + core-js 3。`@babel/preset-env` 的 targets 设为 `chrome: "77"`，由工具链自动完成语法转换与 polyfill 注入。
2. **CSS 兼容**：使用 PostCSS + Autoprefixer，`.browserslistrc` 配置 `chrome >= 77`。优先使用 `-webkit-` 前缀。Flex `gap` 等不可降级特性用 margin 间距替代（详见附录）。
3. **逐项核查 Web API**：每引入一个新 Web API，通过 MDN 兼容性表格或 caniuse.com 单独确认 Chrome 77 支持状态。
4. **真实内核验证**：开发期建议使用 Chrome 77 便携版直接调试，不能仅依赖 Babel 转译后的代码在最新版 Chrome 中跑通。
5. **qwebchannel.js 不要自带**：该文件由框架在运行时自动注入，插件目录中**不需要**携带或引用，也不应修改其内容。

## 三、开发范式

### 3.1 文件结构规范

每个插件以**独立目录**为交付单位，最小结构如下：

```
sample_plugin/
├── config.json    # 插件配置文件（必须）
└── index.html     # 前端入口文件（必须）
```

目录内可自由增加子目录与静态资源（图片、CSS、额外 JS、Lua 脚本等）。`config.json` 是框架识别和加载插件的唯一依据，缺失则插件不会出现在编辑器菜单中，**且没有错误提示**。

### 3.2 config.json 规范

#### 必填字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `name` | string | 插件名称，用于菜单项显示和内部标识 |
| `version` | string | 语义化版本号，如 `"1.0.0"` |
| `entry` | string | 入口 HTML 的相对路径（相对于 `config.json` 所在目录） |

缺少任意必填字段，编辑器加载时会**直接跳过**该插件——不显示、不报错。开发阶段容易漏查，需格外注意。

#### 选填字段与默认值

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `description` | string | `""` | 插件简要描述，显示在插件管理面板 |
| `category` | string | `"default"` | 一级菜单分类，相同值的插件归入同一子菜单 |
| `ui.window_title` | string | 取 `name` 的值 | 窗口标题栏文本 |
| `ui.is_docked` | boolean | `false` | 是否 dock 模式（`false` 为独立浮动窗口） |
| `ui.size` | `[int, int]` | `[1024, 768]` | 初始窗口尺寸 `[width, height]`，单位像素 |

#### entry 路径规则

* 必须使用相对路径，后端自动解析为绝对路径，**不支持**绝对路径写法
* 路径中**不应**包含 `..` 跳出插件目录的上级引用
* 入口文件不存在时，插件被静默跳过

#### 完整示例

```json
{
  "name": "UGC Eggitor Plugin",
  "version": "1.0.0",
  "description": "Advanced editing tools",
  "category": "default",
  "entry": "index.html",
  "ui": {
    "window_title": "UGC Eggitor Plugin Window",
    "is_docked": false,
    "size": [1024, 768]
  }
}
```

### 3.3 入口文件与 backendReady 事件

框架在页面 DOM 加载完成后**自动**完成两件事：注入 `qwebchannel.js` 通信脚本、建立与后端 `PluginInterface` 实例的 WebChannel 连接。整个初始化对前端透明，不需要写任何连接代码。

`window.backend` 就绪后，框架在 `document` 上派发 `backendReady` 自定义事件。**所有依赖 `window.backend` 的业务逻辑必须在此事件之后执行**。

```js
// 推荐写法：监听 backendReady 事件
document.addEventListener('backendReady', function() {
  console.log('后端连接成功');
  init();
});

// 兼容写法：处理脚本可能在事件触发后才执行的场景（如动态加载模块）
if (window.backend) {
  init();
} else {
  document.addEventListener('backendReady', function() { init(); });
}
```

**不要**在 `DOMContentLoaded`、`window.onload` 或页面顶层代码中直接调用 `window.backend`——此时 WebChannel 初始化尚未完成，`window.backend` 为 `undefined`，会抛出运行时异常。

对单文件插件，使用推荐写法即可。对包含多个 JS 文件、动态模块加载的复杂插件，统一使用兼容写法更安全。

### 3.4 后端接口类定义

后端通过继承 `QObject` 的 `PluginInterface` 类暴露能力，所有可从前端调用的方法均以 `@pyqtSlot` 装饰器声明，`result='QVariant'` 允许返回任意可 JSON 序列化的类型：

```python
class PluginInterface(QObject):

    @pyqtSlot(str, list, result='QVariant')
    def runEditorAPI(self, api_name, arg_list):
        """
        统一的编辑器 API 调用入口
        :param api_name: API 方法名
        :param arg_list: 参数列表
        :return: {'success': bool, 'result'|'error': any}
        """
        ...

    @pyqtSlot(str, result=str)
    def runLuaScript(self, path):
        # 执行指定路径的 Lua 脚本，返回执行结果字符串
        ...

    @pyqtSlot(str, result='QVariant')
    def navigateTo(self, path):
        # 在当前插件窗口内切换到另一个 HTML 页面
        ...

    @pyqtSlot(result='QVariant')
    def listHtmlFiles(self):
        # 列出插件目录下所有 HTML 文件，返回 [{name, path}, ...]
        ...

    @pyqtSlot(result='QVariant')
    def testConnection(self):
        # 连接测试接口，验证前后端通信是否正常
        ...
```

### 3.5 标准化返回格式

除 `runLuaScript` 之外，所有接口的 callback 都接收同一结构的返回对象：

```python
# 成功
{'success': True, 'result': result_message}

# 失败
{'success': False, 'error': error_message}
```

前端判断时**必须使用严格相等 `=== true`**，不要用 `if (result.success)` 这样的真值判断，避免某些场景下 `success` 为非布尔真值导致误入成功分支。

### 3.6 自动类型转换

WebChannel 通信时，前端只需传 JS 基础类型，后端按目标 API 的参数类型描述（EdAPIDef）自动完成 JS → Python / 引擎类型的转换。

#### 前后端 EType 映射

| 前端 JS 类型 | 后端 EType / Python 类型 | 转换说明 |
| --- | --- | --- |
| `string` | `Str` / `String` | 自动 UTF-8 编码处理 |
| `number`（整数） | `Int` / `Int32` | 整数转换 |
| `number`（浮点） | `Float` / `Fixed` | 浮点 / 定点数转换 |
| `boolean` | `Bool` | 布尔值映射 |
| `Array` | `List` / `ListXXX` | 数组转换，元素递归 |
| `Object` | `Dict` | 字典对象转换，键值对递归 |
| `[x, y, z]` 或 `(x, y, z)` | `Vector3` / `Point3` | 3D 坐标，必须 3 元素 |
| `null` / `undefined` | `None` | 空值统一处理 |

#### 类型转换的关键风险

* **大整数精度丢失**：JS 的 `number` 是 IEEE 754 双精度浮点，安全整数范围为 $-(2^{53}-1)$ 到 $2^{53}-1$。超出范围的整数（如部分资源 ID、哈希值）传递时会**不可恢复地丢失精度**。建议改用字符串传递，由后端解析为整数。
* **`undefined` → `None`**：函数参数缺省或对象属性缺失时，JS 中为 `undefined`，经 WebChannel 转为 Python `None`。如果后端 API 不预期接收 `None`，可能触发 `TypeError`。前端在调用前应显式检查并赋默认值。
* **循环引用**：包含循环引用的 JS 对象在序列化阶段直接抛 `TypeError: Converting circular structure to JSON`，调用不会到达后端。规避：传参前 `JSON.parse(JSON.stringify(obj))` 做深拷贝。
* **浮点精度漂移**：`0.1 + 0.2 !== 0.3` 在坐标传递中尤为常见。建议对坐标做合理小数位截断，如 `parseFloat(value.toFixed(4))`。
* **中文字符串**：自动 UTF-8 编码，无需手动处理。但若字符串中包含手动转义的 Unicode 序列（`\u0000`），需确保转义格式正确。
* **3D 坐标双格式**：数组 `[x, y, z]` 与对象 `{x: 0, y: 2, z: 0}` 等效。建议项目内统一一种写法（推荐数组）以保持代码一致。

## 四、API 参考

### 4.1 runEditorAPI

所有编辑时功能调用的统一入口。

**前端调用签名**

```js
window.backend.runEditorAPI(apiName, args, callback);
```

**参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `apiName` | string | 是 | 编辑器 API 方法名，与 EdAPIDef 中定义一致 |
| `args` | Array | 是 | 参数列表，元素类型参见 3.6 EType 映射 |
| `callback` | function | 是 | 异步回调，接收标准化返回对象 |

**返回（callback 参数）**

```json
// 成功
{ "success": true, "result": "<任意返回值>" }

// 失败
{ "success": false, "error": "<错误描述>" }
```

**调用约束**

PyQt5 WebChannel **仅支持异步调用**。所有后续业务逻辑必须在 callback 内部或通过 Promise 包装后继续，**不能**在调用语句之后同步获取返回值。

**示例：基础参数与复杂参数**

```js
// 创建障碍物（基础参数）
window.backend.runEditorAPI('create_obstacle', [
  102818,            // ObstacleKey (Int)
  [0.0, 2.0, 0.0]    // Position (Vector3)
], function(result) {
  if (result && result.success === true) {
    console.log('创建成功:', result.result);
  } else {
    console.error('创建失败:', result ? result.error : '未知错误');
  }
});

// 查询单位
window.backend.runEditorAPI('query_unit_ids', [
  "方块",   // Pattern (String)
  true      // UseRegex (Bool)
], function(result) {
  if (result && result.success === true) {
    console.log('查询到', result.result.length, '个单位');
  }
});

// 复杂嵌套参数
window.backend.runEditorAPI('create_complex_object', [
  "building_001",
  {
    "type": "house",
    "size": [10, 8, 12],
    "materials": ["wood", "stone"],
    "enabled": true
  },
  [
    [0, 0, 0],
    [10, 0, 0],
    [0, 0, 10]
  ]
], function(result) {
  if (result && result.success === true) {
    console.log('对象创建成功');
  }
});
```

### 4.2 runLuaScript

执行指定路径的 Lua 脚本文件。

**前端调用签名**

```js
window.backend.runLuaScript(path, callback);
```

**返回说明**

与 `runEditorAPI` 不同，`runLuaScript` 的 callback 接收的是**字符串**（`result=str`），而非结构化对象。错误信息约定包含 `"Error"` 字样，可用 `indexOf` 判断是否执行失败。

**示例**

```js
function runLuaScript() {
  var path = document.getElementById('pathInput').value;
  if (!path) {
    showResult('scriptResult', '请输入脚本路径！', true);
    return;
  }
  try {
    window.backend.runLuaScript(path, function(result) {
      var isError = result.indexOf('Error') !== -1;
      showResult('scriptResult', '执行结果: ' + result, isError);
    });
  } catch (e) {
    console.error('调用错误:', e);
    showResult('scriptResult', '调用失败: ' + e.message, true);
  }
}
```

### 4.3 navigateTo

在当前插件窗口内切换到另一个 HTML 页面。

**前端调用签名**

```js
window.backend.navigateTo(path, callback);
```

**参数说明**：`path` 为目标 HTML 文件的绝对路径；`callback` 接收标准化返回对象。

**重要**：导航后当前页面上下文将被销毁——所有 JS 变量、事件监听器、定时器、未完成的 API 调用回调，都不会保留到新页面。`navigateTo` 适合作为多页面插件之间的页面级跳转，**不适合**做高频视图切换。轻量切换建议用 CSS `display` 控制或 JS 模板渲染。

```js
window.backend.navigateTo('abspath/plugin_dir/settings.html', function(result) {
  if (result && result.success === true) {
    console.log('页面切换成功');
  } else {
    console.error('切换失败:', result ? result.error : '未知错误');
  }
});
```

### 4.4 listHtmlFiles

列出当前插件目录下所有 HTML 文件，常用于构建页面切换的下拉选单。返回数组每项格式为 `{name: string, path: string}`。

```js
window.backend.listHtmlFiles(function(result) {
  if (result && result.success === true) {
    var files = result.result;
    var select = document.getElementById('fileSelect');
    select.innerHTML = '';
    for (var i = 0; i < files.length; i++) {
      var opt = document.createElement('option');
      opt.value = files[i].path;
      opt.textContent = files[i].name;
      select.appendChild(opt);
    }
  }
});
```

返回值中每项的 `path` 可直接作为 `navigateTo` 的参数，构成"扫描目录 → 展示列表 → 点击跳转"的完整流程。

### 4.5 testConnection

验证前后端 WebChannel 通信链路是否正常。建议在 `backendReady` 事件触发后首先调用，作为插件初始化的健康检查。若此接口无响应或 callback 未触发，说明 WebChannel 建立失败，需检查 `backendReady` 是否已触发以及 `window.backend` 是否可访问。

```js
window.backend.testConnection(function(result) {
  if (result && result.success === true) {
    console.log('连接正常');
  } else {
    console.error('连接异常');
  }
});
```

正式插件的生产代码中通常不需要保留该调用，建议仅在调试构建中保留。

## 五、异常与错误处理规范

### 5.1 两类异常的区分

插件开发中需要明确区分两个层面的异常，混淆两者会导致错误处理逻辑出现遗漏：

* **同步异常（`try/catch` 层面）**：调用 `window.backend.xxx(...)` 时同步抛出的错误，例如 `window.backend` 为 `undefined`（backendReady 未触发就调用）、参数包含循环引用导致序列化失败等。这类异常通过 `try/catch` 捕获。
* **异步错误（callback 层面）**：API 调用发出后，后端执行过程中返回的错误，体现为 callback 收到 `{success: false, error: "..."}` 的响应。这类错误**不会**被外层 `try/catch` 捕获，必须在 callback 内判断 `result.success` 处理。

### 5.2 推荐的统一封装模式

建议将 API 调用封装为统一的 `safeCallAPI` 函数，三层防御一次性覆盖：前置校验 → 调用异常捕获 → 业务结果判断。

```js
function safeCallAPI(apiName, args, elementId) {
  // 第一层：前置校验
  if (!window.backend) {
    showResult(elementId, '后端未就绪，请等待 backendReady 事件', true);
    return;
  }
  if (!apiName || typeof apiName !== 'string') {
    showResult(elementId, 'API 名称无效', true);
    return;
  }
  if (!Array.isArray(args)) {
    showResult(elementId, '参数必须为数组', true);
    return;
  }

  // 第二层：调用异常捕获
  try {
    window.backend.runEditorAPI(apiName, args, function(result) {
      // 第三层：业务结果判断
      if (result && result.success === true) {
        showResult(elementId, '成功: ' + JSON.stringify(result.result), false);
      } else {
        var errorMsg = (result && result.error) ? result.error : '未知错误';
        showResult(elementId, '失败: ' + errorMsg, true);
      }
    });
  } catch (e) {
    console.error('调用异常:', e);
    showResult(elementId, '调用异常: ' + e.message, true);
  }
}
```

### 5.3 关键失败场景与应对

#### 5.3.1 WebChannel 通信中断

WebChannel 是进程内 IPC 通信，不是真实网络调用，因此不存在传统的"网络超时"。但以下情况会导致回调延迟或永远不触发：

* QtWebEngine 渲染进程崩溃 → 回调永远不触发
* 后端 Python 线程长时间阻塞 → 回调延迟到阻塞解除后才触发
* 页面被 `navigateTo` 切换或窗口关闭 → 当前页面上下文销毁，未完成的 API 调用回调丢失

**应对**：对关键操作实现超时检测。Chrome 77 不支持 `AbortController` 的信号机制，需用 `setTimeout` 手动实现：

```js
function callWithTimeout(apiName, args, callback, timeoutMs) {
  var called = false;
  var timer = setTimeout(function() {
    if (!called) {
      called = true;
      callback({ success: false, error: '调用超时（' + timeoutMs + 'ms）' });
    }
  }, timeoutMs);

  try {
    window.backend.runEditorAPI(apiName, args, function(result) {
      if (!called) {
        called = true;
        clearTimeout(timer);
        callback(result);
      }
    });
  } catch (e) {
    if (!called) {
      called = true;
      clearTimeout(timer);
      callback({ success: false, error: '调用异常: ' + e.message });
    }
  }
}
```

#### 5.3.2 序列化失败

参数包含循环引用、`Symbol`、`Function` 等不可序列化类型时，WebChannel 序列化阶段会抛出异常。此类错误会被外层 `try/catch` 捕获。调用前可对复杂对象做序列化预检：

```js
function isSerializable(obj) {
  try {
    JSON.stringify(obj);
    return true;
  } catch (e) {
    return false;
  }
}
```

#### 5.3.3 类型转换异常

后端按 EdAPIDef 自动转换类型，当实际值与预期类型不符可能出现：字符串传给 `Int` 参数 → `int()` 转换失败；二元素数组传给 `Vector3` → 长度校验失败；`NaN` / `Infinity` 传给数值参数 → 行为不确定。

前端调用前做类型与范围校验：

```js
function validatePosition(pos) {
  if (!Array.isArray(pos) || pos.length !== 3) {
    return '坐标必须为 3 元素数组';
  }
  for (var i = 0; i < 3; i++) {
    if (typeof pos[i] !== 'number' || isNaN(pos[i]) || !isFinite(pos[i])) {
      return '坐标元素必须为有限数值';
    }
  }
  return null;
}
```

#### 5.3.4 页面卸载与状态丢失

`navigateTo` 调用或用户关闭窗口时，当前页面 JS 执行环境被销毁。所有 `setTimeout` / `setInterval` 自动清除；未完成的 API 调用回调将永远丢失。如有需要跨页面保持的状态，可使用 `localStorage`（Chrome 77 支持）或通过后端持久化：

```js
window.addEventListener('beforeunload', function() {
  try {
    localStorage.setItem('plugin_state', JSON.stringify(currentState));
  } catch (e) {
    // localStorage 写入可能因容量限制失败，静默处理
  }
});
```

### 5.4 常见错误场景速查

| 错误场景 | 现象 | 处理建议 |
| --- | --- | --- |
| `window.backend` 未就绪即调用 | `TypeError: Cannot read property` | 业务逻辑放在 `backendReady` 之后 |
| `config.json` 缺必填字段 | 插件未出现在菜单，无报错 | 检查 `name`/`version`/`entry` 完整性 |
| `entry` 指向不存在的文件 | 插件被跳过，无提示 | 核查相对路径拼写，注意大小写 |
| 传入循环引用对象 | callback 收 error 或同步抛错 | `JSON.parse(JSON.stringify(obj))` 深拷贝 |
| JS 大数值精度丢失 | 整数结果不符预期 | 改用字符串传递，由后端转换 |
| Lua 脚本执行失败 | callback 字符串含 `"Error"` | 检查脚本路径与 Lua 语法 |
| 重复绑定 `backendReady` | 多次开关后触发多次初始化 | 用 `{ once: true }` 或在回调中区分初始化逻辑 |
| 回调收到 `null` | 直接访问属性导致崩溃 | 一律 `result && result.success === true` |

### 5.5 前端 UI 反馈辅助函数

```js
function showResult(elementId, message, isError) {
  var resultDiv = document.getElementById(elementId);
  if (!resultDiv) {
    console.warn('目标元素不存在:', elementId);
    return;
  }
  resultDiv.style.display = 'block';
  resultDiv.className = isError ? 'result error' : 'result';
  resultDiv.textContent = (typeof message === 'object')
    ? JSON.stringify(message, null, 2)
    : String(message);
}
```

## 六、编辑器导入与运行流程

### 6.1 导入步骤

1. 在编辑器菜单中打开**插件管理**面板
2. 点击**导入插件**按钮
3. 在文件选择对话框中定位并选择插件目录下的 `config.json`
4. 编辑器解析配置并将插件注册到对应 `category` 菜单下

导入成功后插件立即可用，**无需重启编辑器**。

### 6.2 打开入口

* **插件管理面板**：导入完成后可直接在管理界面点击打开
* **编辑器菜单**：按 `category` 值归入对应子菜单访问
* **游戏内运行时**：编辑器支持在游戏内（运行态）使用插件，入口与编辑态一致

### 6.3 加载时序

```
编辑器启动
  ↓
扫描已注册插件的 config.json
  ↓
校验必填字段（name / version / entry）
  ↓
校验 entry 指向的文件是否存在
  ↓
注册到菜单系统
  ↓
（用户点击插件菜单项）
  ↓
按 ui.size / ui.is_docked 创建 QWebEngineView
  ↓
实例化 PluginInterface 并注册到 WebChannel
  ↓
加载 entry 指定的 HTML
  ↓
自动注入 qwebchannel.js，初始化通信通道
  ↓
触发 backendReady 事件，window.backend 就绪
  ↓
插件前端代码开始执行业务逻辑
```

任一校验步骤失败，该插件被静默跳过，**不影响**其他插件加载。`backendReady` 是插件生命周期中唯一需要主动感知的时机点。

## 七、示例插件解读

### 7.1 文件位置与结构

示例插件位于工程目录：

```
season\client\script\editor\editor_new\view\webview\ugc_plugin\sample
```

目录结构：

```
sample/
├── config.json    # 标准配置文件
├── index.html     # 主界面：API 测试按钮 + 结果展示
└── test.lua       # Lua 测试脚本，验证 runLuaScript
```

### 7.2 设计意图

示例插件本质上是一个"**API 联调面板**"：核心目标是**验证前后端联调流程**，而不是演示某个具体业务功能。它封装了若干 EditorAPI 调用，每条对应界面上一个触发按钮，开发者点击后观察返回结果，快速确认通信链路是否正常。

它同时演示了 `navigateTo` + `listHtmlFiles` 的页面导航联动，展示多页面插件的组织方式；`test.lua` 提供了一个可被 `runLuaScript` 直接调用的脚本样本。

### 7.3 推荐的入手路径

对第一次接触插件系统的开发者，推荐以下路径：

1. 将 `sample` 目录按第六章的导入步骤导入编辑器，确认菜单中出现该插件
2. 打开插件窗口，逐一点击 API 测试按钮，核查每条 API 的返回值
3. 基础链路跑通后，**整体复制 `sample` 目录**为新插件起点
4. 仅修改 `config.json` 的 `name` 和 `version`，替换 `index.html` 为自己的实现
5. 保留 `test.lua` 作为 Lua 脚本调用的参照

"复制 + 替换 index.html" 是最低成本的起步方式：不需要从零搭建项目结构，`config.json` 与 Lua 脚本调用关系都已验证，只需专注 H5 界面与 API 调用逻辑。

### 7.4 可直接复用的前端模式

示例插件展示了几个可直接拷走的前端模式：

```js
// 1. 初始化入口
document.addEventListener('backendReady', function() {
  console.log('后端连接成功');
  initPluginUI();
});

// 2. 输入校验 + API 调用
function createObstacle() {
  var obstacleKey = parseInt(document.getElementById('obstacleKey').value);
  if (isNaN(obstacleKey)) {
    showResult('createResult', '请输入有效的组件编号！', true);
    return;
  }
  var x = parseFloat(document.getElementById('posX').value);
  var y = parseFloat(document.getElementById('posY').value);
  var z = parseFloat(document.getElementById('posZ').value);
  window.backend.runEditorAPI('create_obstacle', [obstacleKey, [x, y, z]],
    function(result) {
      if (result && result.success === true) {
        showResult('createResult', '创建成功: ' + result.result, false);
      } else {
        showResult('createResult',
          '创建失败: ' + (result ? result.error : '未知错误'), true);
      }
    });
}
```

`showResult` 函数（见 5.5 节）在任何插件中都可直接沿用或稍作样式调整。

## 八、最佳实践与开发建议

### 8.1 开发前检查清单

动手写代码前，对照以下清单确认环境与配置就绪：

* [ ] `config.json` 包含 `name`、`version`、`entry` 三个必填字段，值不为空
* [ ] `entry` 使用相对路径，且对应文件实际存在于目录中
* [ ] 前端依赖的 JS / CSS 特性已逐项对照 Chrome 77 兼容表核查
* [ ] 如引入构建工具，已配置 Babel + core-js 3 与 PostCSS + Autoprefixer
* [ ] 所有业务逻辑初始化放在 `backendReady` 回调内，不在顶层直接访问 `window.backend`
* [ ] 每个 `runEditorAPI` 调用都有 `result.success === true` 严格判断
* [ ] 所有 API 调用封装了 `try/catch`

### 8.2 异步流程与回调扁平化

WebChannel 仅支持回调模式，多个 API 串行调用容易形成嵌套。Chrome 77 原生支持 `Promise`，用 Promise 包装可扁平化调用链；注意 `async/await` 需要 Babel 编译，若不引入构建工具，直接用 `.then` 链是更安全的选择。

```js
function callEditorAPI(apiName, args) {
  return new Promise(function(resolve, reject) {
    try {
      window.backend.runEditorAPI(apiName, args, function(result) {
        if (result && result.success === true) {
          resolve(result.result);
        } else {
          reject(new Error(result ? result.error : '未知错误'));
        }
      });
    } catch (e) {
      reject(e);
    }
  });
}

// 串行
callEditorAPI('query_unit_ids', ["方块", true])
  .then(function(ids) {
    return callEditorAPI('batch_transform', [ids, { scale: 2 }]);
  })
  .then(function() {
    showResult('output', '批量变换完成', false);
  })
  .catch(function(err) {
    showResult('output', '流程失败: ' + err.message, true);
  });
```

`Promise.allSettled` 在 Chrome 77 不可用。需要并行执行多个调用并分别处理各自成功/失败时，用 `Promise.all` 配合每个 Promise 内的 `.catch()` 包装：

```js
var tasks = [
  callEditorAPI('api_a', argsA).catch(function(e) { return { _error: e }; }),
  callEditorAPI('api_b', argsB).catch(function(e) { return { _error: e }; })
];
Promise.all(tasks).then(function(results) {
  results.forEach(function(r, i) {
    if (r._error) {
      console.log('任务', i, '失败:', r._error.message);
    } else {
      console.log('任务', i, '成功:', r);
    }
  });
});
```

### 8.3 性能注意事项

* **避免高频调用**：不要在循环中直接 `runEditorAPI`，WebChannel 序列化/反序列化有固定开销。批量操作优先使用后端聚合接口或 Lua 脚本批处理。
* **DOM 批量更新**：DOM 操作量大时使用 `DocumentFragment` 或一次性 `innerHTML` 赋值，减少重排重绘。
* **`navigateTo` 不适合频繁切换**：会完整销毁并重建页面上下文。轻量视图切换用 CSS `display` 控制或 JS 模板渲染。

### 8.4 安全与健壮性

* **不要硬编码敏感信息**：插件代码客户端可见，密钥、内部服务地址等不应硬编码
* **防御性使用返回值**：协议约定 `result.result` 的结构，但仍应做类型检查，避免后端异常返回导致前端崩溃
* **假设可被随时关闭**：用户点关闭、编辑器退出，关键数据不应仅保存在内存中

### 8.5 避免重复绑定事件监听器

插件窗口关闭后重新打开，`backendReady` 会再次触发。如果在事件监听器内动态绑定 DOM 事件或定时器且没有清理，会导致重复绑定。把握一个原则：**DOM 事件绑定放在 `DOMContentLoaded`，后端相关初始化放在 `backendReady`**。

```js
// 错误：每次 backendReady 都追加 click 监听器
document.addEventListener('backendReady', function() {
  document.getElementById('btn').addEventListener('click', handleClick);
});

// 正确：分离
document.addEventListener('DOMContentLoaded', function() {
  document.getElementById('btn').addEventListener('click', handleClick);
});

document.addEventListener('backendReady', function() {
  loadInitialData();
});
```

### 8.6 版本管理建议

`config.json` 的 `version` 当前主要用于显示，但建议从一开始就严格遵循语义化版本（SemVer）：

* `PATCH`（`1.0.0 → 1.0.1`）：bug 修复，不改变接口行为
* `MINOR`（`1.0.0 → 1.1.0`）：新增功能，向后兼容
* `MAJOR`（`1.0.0 → 2.0.0`）：破坏性变更，接口或行为不再向后兼容

养成每次交付更新版本号的习惯，便于在编辑器插件列表中区分同名插件的不同版本，也为后续可能引入的版本管理机制做好准备。

### 8.7 上线前验证清单

### 8.8 常见踩坑

复盘开发实践中高频出现的易错场景：

**坑 1：在 backendReady 触发前访问 window.backend** 脚本若在 WebChannel 连接建立前就调用 `window.backend.runEditorAPI(...)`，会因 `window.backend` 未初始化抛 `TypeError`。必须放在 `backendReady` 回调中，或使用兼容判断。

**坑 2：把异步调用当同步使用**

```js
var result = window.backend.runEditorAPI('some_api', args);
console.log(result); // 永远是 undefined
```

从同步思维切换到异步思维时最常见的错误。必须用回调。

**坑 3：回调参数为 null 时直接访问属性** WebChannel 通信异常时回调可能收到 `null`。直接 `result.success` 会让整个回调崩溃。一律使用 `result && result.success === true`。

**坑 4：entry 路径错误导致插件静默消失**`entry` 必须是相对于 config.json 所在目录的相对路径。绝对路径、含盘符、文件不存在时，插件被静默跳过，菜单中不出现且无错误提示。

**坑 5：大数值传递精度丢失** JS Number 是双精度浮点。传递大型组件 ID 或哈希值（超 $2^{53}-1$）时被截断。改用字符串传递。

**坑 6：循环引用导致序列化崩溃** DOM 节点、函数引用、对象间互引都会导致 `JSON.stringify` 抛错。传给 `runEditorAPI` 的对象必须是纯数据。

**坑 7：CSS Flex `gap` 静默失效** Chrome 77 遇到 Flex 容器上的 `gap` 不会报错而是直接忽略。用 `* + * { margin-left: ... }` 替代。

**坑 8：config.json JSON 语法错误无明确提示** 尾逗号、注释、非标准引号等 JSON 语法错误时，解析直接失败，插件不可见。提交前用 `JSON.parse(...)` 或 IDE 的 JSON 校验确认。

## 附录 A：Chrome 77 兼容写法速查

| 不兼容写法 | Chrome 77 替代方案 |
| --- | --- |
| `obj?.prop` | `obj && obj.prop` |
| `value ?? fallback` | `value !== null && value !== undefined ? value : fallback` |
| `arr.at(-1)` | `arr[arr.length - 1]` |
| `str.replaceAll(a, b)` | `str.split(a).join(b)` |
| `structuredClone(obj)` | `JSON.parse(JSON.stringify(obj))`（不含函数 / 循环引用） |
| `Promise.allSettled(ps)` | `Promise.all(ps.map(p => p.then(v=>({status:'fulfilled',value:v})).catch(e=>({status:'rejected',reason:e}))))` |
| `globalThis` | `window`（浏览器环境等价） |
| `gap: 8px;`（Flex 容器） | 子元素加 `margin`，父元素负 `margin` 补偿；或 `* + * { margin-left: 8px }` |
| `clamp(min, val, max)` | JS 动态设置或固定值 |
| `aspect-ratio: 16/9` | padding-top 百分比 hack（如 `padding-top: 56.25%`） |
| `:has(...)` / `:is(...)` / `:where(...)` | 改用 class 组合与后代选择器 |
| `AbortController` 异步取消 | 手动 `setTimeout` 标记 + `clearTimeout` |

## 附录 B：插件与 UGC 生态协同

插件系统的长线价值不只在"能做什么"，更在"能被复用"。一个构思良好的插件完成后，应被视为 UGC 创作链条上的生产力节点：

* **单次操作 → 批量自动化**：将原本逐个放置和调整的重复操作封装为一次按钮点击。例如批量铺设地形纹理、按预设规则排列关卡元素、一键替换素材库中指定类别资产。
* **专业知识下沉**：将高级创作者掌握的复杂编辑器操作封装为带直观 UI 的插件。中腰部创作者无需理解底层 API，点按按钮即可复现资深开发者的操作流程——这缩小了头部与中腰部创作者之间的生产力差距。
* **工作流固化为可分发模块**：工作室内部通过插件将成熟制作管线打包。新成员或外部合作方导入插件即获得完整工具链，减少口头传授和文档阅读的磨合成本。
* **社区驱动创新**：当门槛降低到"写 HTML + 配 JSON"，编辑器不再是封闭黑盒。社区创作者可基于开放 API 发明官方未曾预见的工具用法，形成"发现需求 → 编写插件 → 社区分享 → 更多人受益"的正向循环。

插件的每一次导入，都是在复用前人的工作经验。这定义了插件系统在《蛋仔派对》UGC 生态中的终极角色：**让创作力可复制、可积累、可传播**。
