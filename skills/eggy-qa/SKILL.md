# 蛋仔地图测试

测试依据是用户需求和可试玩验收，不从当前代码反推需求。静态检查、代理可执行验证和用户试玩必须分开表述。

## 开发决策驱动的测试批次

测试不是跨任务常驻模式。先写清当前卡点和证据将决定的下一步动作，再按“准备 → 集中取证 → 决策 → 退出”执行一个最小充分批次。

- 没有当前已授权的试玩和未决开发卡点时，不为以后可能测试预先增加打印、测试函数或测试文件。
- 同一运行条件下，入口、关键参数或状态、目标对象、玩家或运行端、分支选择和最终结果等关联观察应一次布置，避免为了单点限制重复启动试玩。
- 观察点数量不设机械上限，但每一项都必须能排除一条候选原因、确认一段关键链路或改变下一步开发动作；与当前决策无关的完整覆盖、边角组合和“顺便测测”不加入。
- 观察点会互相改变状态、日志混在一起无法归因、需要不同玩家或运行端隔离，或失败风险差异明显时才拆分。
- 证据足以选择下一步、无法安全继续取证、已经阻塞或等待用户操作时退出。证据仍不足时，可以在同一批次补充能直接区分剩余路线的观察，但不能借机扩写正式功能或测试工程。
- 正式修复后可以重新验证同一验收目标，但要说明代码变化为什么使旧证据失效；仅仅“还想更稳”不构成新批次。
- 项目已有的长期测试套件，或用户明确要求交付的正式测试，不作为临时残留删除；但对应断言写完并得到结果后，同样退出测试阶段。

本状态机覆盖本技能下所有界面测试等专题参考。专题资料中的旧“自动进入测试”“连续修复重跑”或固定轮数要求一律无效，只能保留其经过当前版本查证的技术信息。

## 选择测试范围

按从小到大的顺序选择第一个足以证明当前改动的方法：

1. 检查本次差异、语法、引用和静态结构。
2. 运行项目已有的单项测试、只读查询或纯逻辑断言。
3. 需要试玩验证代码行为时，先在现有正式调用点补足可判定的最小测试打印。
4. 用户明确授权启动试玩后，只验证本次修改的一个入口、状态、对象或玩家流程。
5. 只有无法安全隔离时才新建测试文件。

小功能不因为“要测试”而新建文件。共享模块、多人状态、存档、公共界面或多文件行为变化时，再扩大相关回归；全量回归只用于广泛公共改动、完整批次收尾或用户明确要求。

## 执行

1. 写清本轮要打通的卡点、证据将决定的下一步、共同前置条件、最短操作、关联观察和预期。
2. 测试需要调用新的编辑器接口时，先按编码技能查证；已有稳定工具命令不重复制造接口证据卡。
3. 功能试玩前确认日志能判断是否进入、关键条件和最终结果；已有日志完整覆盖时复用，否则只加入本轮所需的最小打印。新增临时测试代码和测试日志必须带 `【测试专用】`。
4. 试玩日志只读取本轮新增区间，相同错误归并，不把历史错误当作当前结果。
5. 界面按当前需求检查典型长短文本、显隐和相邻控件；多人功能必须明确验证了几个玩家和效果发给谁。本次涉及玩家交互时，在同一批次选相关的成功、失败或等待场景，检查玩家能否感知真实结果、有无误报成功、刷屏或开发诊断外露；已有表现足够时不要求新增提示，日志通过不能代替体验验证，不为此另开试玩或测试文件。
6. 性能结论要有触发场景、对象规模和观察证据，不能只写“不卡”。

接口能力、参数关系、对象、运行端或生命周期不明，或者首次调用报错、无效果时，停止扩大测试并读取 `eggy-api-research`。每轮只改变当前假设所需的最小内容，不直接重写全量正式代码。

## 结果

结果只使用：未测试、通过、失败、无法区分、部分验证、阻塞、待用户试玩。

- 日志没有新增报错，只能说明本轮未捕获新报错。
- 自动检查通过但无法验证真实操作、视觉、手感或多人表现时，写“部分验证”或“待用户试玩”。
- 用户没有确认整个计划完成时，不得标记完成。

证据足以支持下一步开发动作后立即退出：需要修复时回到正式代码，不在测试阶段继续扩写实现；需要用户操作时停止改文件并给出最短步骤；其余情况删除本轮临时测试内容并重新做一次静态检查。部分结果或无法区分若仍卡住开发，只补直接影响决策的观察；如果没有这种观察就报告阻塞。收尾前搜索本轮修改文件中的 `【测试专用】`：只有正在等待用户执行的已授权试玩可以保留，并必须逐项说明用途；其他残留全部清理。

普通测试过程不写长期文档。只在完整批次达到待试玩、用户反馈、发现需要跨会话继续的阻塞，或验收标准发生变化时更新当前任务载体。原始日志、每次命令和重复失败不落盘。

向用户简洁说明验证范围、实际结果、失败或阻塞、最高验证等级和最短试玩步骤。
