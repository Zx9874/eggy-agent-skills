# 根 README 项目总览规范

根 `README.md` 是新代理进入地图后的第一张导航图，目标是几分钟内回答：玩家怎么玩、主要系统有哪些、当前代码怎样运行、关键状态归谁管理、详细资料去哪里查。它不是第五份需求文档，也不是开发日志。

## 事实来源

- 玩法、人数、胜负、核心循环和玩家可见规则：以当前工程的 `docs/需求文档.md` 为准。
- 已实现入口、模块、事件、状态、跨端关系和存档：以当前工程代码、配置及已确认编辑器绑定为准。
- 进行中和未来内容：只指向当前工程的 `docs/开发计划.md` 或当前任务文件，不写进“当前实现架构”。
- 实例、预设、界面节点和资源编号：只指向当前工程的 `docs/资产清单.md`，不复制进总览。
- 外部契约：总览只摘要调用方向和所属系统，不列完整函数名、参数、返回值或蛋码变量表；详细关系以代码注解、导出扫描结果和对应独立任务文件为准。
- 事实冲突时写明差异并停止静默合并；禁止把代码现状升级成玩法需求，也禁止把计划中的方案画成已经实现。

## 创建方法

1. 确认地图名称、原点版或世界版、目标人数和当前游玩状态。
2. 读取需求文档标题、地图定位、核心循环和主要系统，不通读与总览无关的细节表。
3. 读取入口文件、自定义一级目录和本次架构相关模块；用定向搜索确认事件、状态所有权、跨端通信、存档和外部契约，不扫描全部函数制造清单。
4. 把玩法和实现分开写，再用“玩法系统 → 当前模块”对应表连接两者。
5. 只在关系靠文字难以看清时使用图；图中的每个节点和箭头都必须有代码或已确认绑定证据，否则删除或标为未知。
6. 已有 `docs/README.md` 时把它视为旧索引：迁移仍有效的唯一链接，停止继续更新旧入口，并把旧文件列为删除候选。只有用户看到候选与引用检查结果并明确确认后才能删除；未确认前保留原文件，禁止静默清理。
7. 创建或更新完成后只读回本次变动的段落，执行下方四项语义检查；不运行独立格式审计。

### 总览缺失时的最小补建输入

总览缺失不是“把所有资料先读一遍”的理由。补建只收集能回答“玩家怎么玩、代码从哪里启动、状态由谁负责、下一步资料去哪里找”的最小证据，按以下顺序读取：

1. 工程路径和版本配置：用路径初判，再读 `eggy.json` 或 `.codemaker/config.json` 二次确认；同时确认目标游玩人数，未知就写“未知”。
2. 项目规则的项目事实：只取地图名称、版本、人数、模块边界、官方文件边界、工具位置和高代价陷阱；根规则和历史流水不复制进总览。
3. 需求文档的导航信息：只取标题、地图定位、核心循环、胜负或长期目标、主要系统名称及其玩家可见结果；系统细节、参数表和资产编号留在原文。
4. 当前工程骨架：读取入口文件、一级自定义目录和每个主要系统的一个代表性入口；只定向搜索状态所有权、跨端关系、存档和外部绑定，不建立函数清单。
5. 开发计划的活跃区：只取活跃任务、收件箱、阻塞和最近正确交接；历史章节、每轮测试和原始日志不进入总览。
6. 世界版额外读取项目中的服务端资源摘要；没有实测数据就写“未知”，不凭经验补内存数字。

补建时把证据分成三类写入：

- **已确认玩法**：只能来自需求文档或用户明确确认。
- **当前实现**：只能来自代码、配置或已确认的编辑器绑定；静态存在但未试玩写“待试玩”。
- **未知或冲突**：原样标出并链接到开发计划，不替两份资料猜一个折中答案。

补建完成后，先保存总览，再只读回总览中受影响的段落和文档链接。不要为了“验证总览完整”重新读取全部需求、资产、接口、历史任务或 `.codemaker/`；下一步开发由总览路由到具体任务后再按需查证。

## 核心内容

总览没有固定标题、表格、行数或图表数量。按地图复杂度用最短内容回答以下问题，不列每个函数：

1. **地图速览**：玩家是谁、主要目标是什么、适合多少人、怎样开始、怎样结束或长期推进。
2. **玩法主循环**：玩家反复做什么、得到什么反馈、如何进入下一阶段。步骤能说清就不用画图；关系复杂时再补玩法图。
3. **主要系统**：玩家行为、结果、当前实现情况和主要实现位置。状态用当前证据能支持的自然语言；证据不足写未知，静态实现齐全但用户尚未试玩写待试玩，只有用户确认后才能写用户确认可用。
4. **当前实现架构**：入口、一级模块、权威状态、关键事件或通信、界面与场景、存档和外部绑定。简单地图用短列表，多个系统或跨端关系难以看清时再画一张架构图。
5. **状态归属**：只有多人、存档、跨端或共享状态较多时才单独建表；简单地图直接写在对应系统下。
6. **文档入口**：链接需求文档、开发计划和资产清单，并写出真正需要的新会话入口文件或目录。

## 版本差异

- **原点版**：总览中明确 `main.lua`、功能模块、帧同步共享状态、蛋码事件或导出契约、界面与场景绑定、存档；没有证据时不编造客户端和服务端分层。
- **世界版**：总览中明确 `server/main.lua`、`client/main.lua`、`common/`、服务端权威状态、客户端显示、跨端事件、世界单位和存档；不能把每玩家显示状态写成全世界共享状态。

## 更新频率

只有以下变化才更新：

- 玩家身份、人数、核心循环、开始或结束方式、主要玩法系统变化。
- 入口文件、一级模块职责、权威状态所有者、客户端和服务端边界、关键事件流、存档边界、外部调用方向、调用方类别或归属系统变化。
- 主要系统的整体实现情况发生足以改变新会话理解的变化。
- 原先标为未知的总览级事实得到可靠确认。

普通数值、文案、单个函数内部实现、局部错误修复、日志和资产编号变化不更新。一次开发批次最多在收尾更新一次，不为每个步骤刷新总览。

## 收尾读回

创建或更新总览后只检查四项，全部能回答就停止；不要把这四项机械地变成对用户的提问：

1. 玩法摘要是否只来自当前需求文档？
2. 当前架构是否都有代码、配置或已确认编辑器绑定证据？
3. 是否把进行中或未来方案误写成已经实现？
4. 需求文档、开发计划和资产清单能否从总览找到？

Git 保存总览的历史。新会话先用总览定向，任务命中某条架构路线时再定向检查当前代码和绑定；无需全库扫描，也不维护额外核对日期。
