# 开发任务文件格式

本文件只在创建、拆分、迁移或收束任务时读取。不得把模板中的空章节机械复制进每个任务。

## 任务索引

`docs/开发计划.md` 是地图级入口，不是全部历史和技术流水。建议只保留以下区域：

```markdown
# 开发任务索引

## 活跃任务

| 编号 | 任务 | 状态 | 负责范围或会话 | 阻塞于 | 任务载体 |
|------|------|------|----------------|--------|----------|

## 收件箱

| 编号 | 用户原话 | 优先级 | 下一次需要决定什么 |
|------|----------|--------|----------------------|

## 简短任务卡

### DEV-YYYYMMDD-NN 任务名称
- 用户原话：
- 代理理解：
- 可试玩验收：
- 状态：
- 下一步：

## 最近确认结果

| 编号 | 结果 | 用户确认日期 | 提交引用 |
|------|------|--------------|----------|
```

规则：

- “活跃任务”允许多行，用于不同功能或不同会话；不要再使用只能容纳一个任务的全局“当前任务卡”。
- “收件箱”只保存用户以后想做的事及下一次需要决定的问题，不提前生成技术步骤。
- “简短任务卡”只用于当前会话可达到待试玩的小任务。任务变复杂时迁移到独立文件，并在原位置只保留指针。
- “最近确认结果”只保留便于恢复方向的少量条目；完整历史由 Git 和已收束任务文件保存。

## 独立任务文件

文件名使用稳定编号：`docs/开发任务/DEV-YYYYMMDD-NN-简短名称.md`。同一天编号递增，任务改名时编号不变。

按任务需要选用以下字段：

```markdown
# DEV-YYYYMMDD-NN 任务名称

- 状态：未开始 / 进行中 / 阻塞 / 待试玩 / 待用户确认 / 用户确认完成 / 用户取消
- 地图与版本：
- 目标游玩人数：
- 负责范围或会话：
- 阻塞于：无，或任务编号列表
- 关联任务：
- 规则版本：
- 动工前恢复依据：通常记录已有 Git 提交号和未提交差异；只有存在 Git 无法覆盖的场景/UI/预设状态时才记录快照路径，不为填写此项新建备份。

## 用户原话

原样保存会影响功能、验收或修改原因的内容。

## 代理理解

用玩家可见结果复述；分开写已确认内容、代理判断和待用户决定内容。

## 可试玩验收

写清前提、玩家操作、应出现的结果，以及必须保持的原有效果。

## 范围

- 本任务负责：
- 本任务不负责：

## 已确认事实与剩余未知

只保存会影响实现方向或下一会话继续的结论；普通接口查证、原始日志和失败流水不写入。

## 最近正确交接

- 当前状态：
- 已排除路线：
- 下一动作：
- 需要用户或编辑器完成的操作：

## 收束摘要

只在达到待试玩或用户确认后填写：实现效果、最高验证等级、最短试玩步骤、遗留问题和提交引用。
```

## 拆分原则

大型功能按“可独立试玩的纵向结果”拆分，而不是按代码层拆分。例如“玩家购买一种商品并正确扣款、获得物品”可以成为一个任务；“先写界面、再写事件、再写存档”不能作为三个彼此不可验收的任务。

每个任务应适合一个新会话独立读取和推进。明确依赖关系：只有阻塞任务已达到要求状态，后续任务才进入可执行范围。没有依赖且资料齐全的任务属于“可执行前沿”。

## 迁移与收束

- 现有大型 `docs/开发计划.md` 不做一次性批量迁移。实际命中某个旧任务时，为它建立任务文件并在索引顶部添加指针；旧章节暂时保留，待自然收束。
- 任务文件达到“待试玩”后继续保留，直到用户给出结果。
- 用户确认完成后，把仍然长期有效的信息迁入对应权威文档。任务文件可以移入 `docs/开发任务/已完成/YYYY/`；不要让新会话默认读取归档目录。
- 小任务确认完成后，将简短任务卡压缩成“最近确认结果”一行。原始过程仍可从 Git 恢复。
- 不为每轮测试、接口尝试、每日报告或外部模型每次调用创建文件。

## 多代理与外部模型

发生真实交接时才记录：会话编号、地图和版本、负责范围、已加载规则版本、最近正确摘要、当前状态以及未解决错误经验。没有参与就不创建空字段。

同一任务同一时间只有一个负责会话。另一个会话可以只读审查，但不得同时编辑任务文件或相同正式代码；需要换手时先完成一次交接更新。
