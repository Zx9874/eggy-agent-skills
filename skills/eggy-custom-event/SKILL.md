# 蛋仔事件通信

本技能只负责把通信协议讲清楚。具体 API、参数类型、同步方式和运行端必须以当前工程定义、对应版本官方资料和官方示例为准。

## 先判定版本和方向

- 原点版：只在当前资料确认的范围内处理 Lua 与蛋码的自定义事件，以及蛋码调用 Lua 函数。
- 世界版：优先按世界版当前的客户端、服务端、公共代码和公开包通信方式处理，不把原点版蛋码事件写法套过来。
- 先写清发送方、接收方、运行端、触发时机、接收范围和数据所有权；不明确就停止实现。

## 协议表

每个事件或请求至少记录：

| 项目 | 内容 |
|---|---|
| 名称 | 当前可视化配置或代码中的准确名称 |
| 方向 | Lua 到蛋码、蛋码到 Lua，或客户端/服务端之间 |
| 参数 | 顺序、当前定义的类型、字段名、含义和是否允许空值 |
| 变量关系 | 两端每个变量对应哪个参数，不能只写“传一个对象” |
| 时序 | 谁先执行、是否同步、是否可能重复或回发 |
| 接收者 | 操作者、指定玩家、附近玩家、全体玩家或服务端 |
| 失败表现 | 不触发、类型不符、空值、重复触发或绑定失效 |

事件名称、导出函数名称和蛋码变量名称必须原样保留。没有必要时，不进行中文名和英文名互改；必须修改时，先向用户说明重新绑定或修改调用方的成本并确认具体名称。

## 强制查证

1. 在当前工程定义中确认每个发送、注册、回调或跨端接口的完整签名。
2. 在对应版本官方手册中确认参数含义、运行位置、前提、范围和失败表现。
3. 在对应版本官方示例中寻找相同方向和相同数据形态的组合。
4. 资料未说明的同步顺序、可传类型、默认值或空值行为保持“未知”，不要凭历史代码补全。
5. 首次失败或无效果时转入接口研究，先区分接口能力、运行端、对象、生命周期、参数和外部配置，不能只围着一个写法反复试。

## 实现边界

- 事件发送和监听不能因为名称相似就自动形成自触发循环；必须明确哪些事件由哪一端监听。
- 请求-响应必须有独立的请求名、响应名、关联标识和超时或失败处理；是否能同步返回由当前资料确认，不能假设。
- 参数表的字段名以对端实际定义为准，类型名和字段名不是一回事。
- 已经绑定的导出函数仍受 `eggy-lua-export`（Lua 外部导出契约）保护；事件技能不允许顺手改函数名或签名。
- 涉及多人时，明确事件是全图广播还是只给某个玩家；不能只验证发送者而忽略其他玩家。

## 最小验证和收尾

- 先选一个代表性事件和一个最短调用链验证方向、参数关系和接收者，再扩大到同类事件。
- 测试代码或临时日志注入地图运行工程时加 `【测试专用】`；证据足够后退出测试模式并清理临时内容。
- 交付前逐项核对事件名、方向、参数顺序、字段名、类型、空值、重复触发和外部绑定。
- 需要用户在蛋码或编辑器中重新绑定时，逐项列出准确名称和操作，不报告为已经完成。
