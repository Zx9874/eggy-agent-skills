# 蛋仔地图完整策划

把模糊创意、零散想法或已有策划逐步变成用户真正确认的完整玩法策划。这个阶段只解决“玩家玩什么、为什么继续玩、各种情况下会发生什么”，不进入代码实现。

原点版与世界版是两套并行且不互通的创作工具，世界如何运转和适合的玩法重点不同。版本是一级策划边界：已有工程直接识别；尚未建工程时在第一轮确认用户是否已经选定版本，未选定则根据核心体验给出建议。版本确定后禁止混用另一版的策划分支。

## 选择起点

- **从零开始**：用户没有工程或只有题材、参考作品、某个组件、一个画面时，从最能定义玩家体验的种子开始，不要求用户先写一份方案。
- **完善想法**：先复述已经明确的玩法，只追问仍会改变体验的父级决定，不把用户说过的内容重新问一遍。
- **审查策划**：先读取现有 `docs/需求文档.md` 和当前任务载体，找出冲突、缺口和无法验收的描述，再从影响最大的一个问题开始。
- **已有工程**：读取项目规则、地图版本、目标人数和相关玩法文档。能从工程、文档或工具查到的事实自行查找，不拿事实问题考用户。

没有工程时仍可完成访谈；不得擅自创建目录。直到需要保存策划案时，再让用户指定地图工程或保存位置。

## 双问题访谈规则

开始访谈时读取 [共用访谈入口](references/interview-map.md)。版本确认后只读取 [原点版策划分支](references/origin-planning.md) 或 [世界版策划分支](references/world-planning.md) 中的一份，不得两份同时加载或互相套用。

1. 每轮默认提出两个编号问题，两个问题必须都处于当前已解锁的决策前沿，不能让第二问依赖第一问尚未得到的答案。
2. 只有当前确实只剩一个关键问题，或所有其他问题都必须等待第一问答案时，才允许这一轮只问一个；不得为了凑两个而加入无关问题。
3. 先解决父级决定，再问依赖它的细节。每轮回答后重算下一轮，不按预先清单机械推进。
4. 每个问题先给一个明确推荐和简短理由；最多再给两个有真实取舍的备选。用户可以回答“1 按推荐，2 第二个”，也可以分别说自己的方案。
5. 两个问题连同推荐尽量控制在六至十二行。只有取舍本身复杂时才展开，禁止用长篇背景淹没问题。
6. 事实由代理查证，决定由用户作出。不得用代理常识、参考游戏惯例或所谓行业默认替用户拍板。
7. 用具体玩家场景检查决定，例如首次进入、两人同时操作、资源不足、掉线重进、完成后再次参与；一轮最多检查两个互不依赖的场景。
8. 不设置固定追问轮数。关键分支没解决就继续问；用户要求暂停或先出草案时，保留待确认项，不用假设填满空白。

## 会话状态

- 当前会话可以完成的短策划只保留在对话中，最终一次写入需求文档。
- 预计跨会话、需要多人接力或用户暂停时，使用工作区自定义的 [任务管理技能](../eggy-dev-plan/SKILL.md) 建立或复用一个策划任务文件。只保存用户原话、已确认决定、剩余问题、最近正确摘要和下一轮两个问题。
- 在一个主题收束、用户暂停、上下文需要交接或最终输出时更新任务载体；不得每回答一个问题就写一次文件。
- 用户改变决定时覆盖玩法真相，并在任务载体保留哪条新决定替代了旧决定；需求文档不保存讨论流水。

## 访谈推进

1. 用一句话说明目前理解和本次采用的起点模式；已有工程同时说明识别到的版本。
2. 尚未选定版本时，第一轮同时询问核心体验和版本是否已经固定；先取得答案，再推荐版本。版本确认后才进入对应分支。
3. 明确这张地图最终要给玩家的核心体验，再按对应版本展开核心循环、玩家关系、流程和相关系统。
4. 每完成一个主题，用不超过三条短句回顾已确认内容，然后进入下一轮两个问题。
5. 发现前后矛盾时立即指出冲突，只让用户决定哪一条有效，不替用户静默合并。
6. 编辑器版本或官方系统能力会改变玩法选择时，先检索对应版本本地官方资料。资料不能证明时标记“能力待查证”，不承诺一定能实现。
7. 共用完整性门禁和当前版本门禁都通过后才允许收束；有关键未知时继续访谈，不提前宣布策划完成。

## 形成策划案

当关键分支已解决时，先给用户一段紧凑的共同理解摘要，并提出最后两个问题：

1. “以上摘要哪些地方准确，哪些地方需要修改？”
2. “是否授权按你本轮给出的修订结果整理成正式策划案？”

用户确认后：

1. 读取并执行工作区自定义的 [玩法需求维护技能](../eggy-design/SKILL.md)，把已确认玩法写入该地图唯一的 `docs/需求文档.md`；本次定案改变地图定位、人数、核心循环或主要系统时，由该技能在同一批次同步根 `README.md` 的玩法摘要，不另建策划总览，也不凭策划推测代码架构。
2. 写清完整游玩流程和每个功能的前提、操作、反馈、成功、失败、重复操作、多人归属及可试玩验收。
3. 将明确不做的内容写入范围边界；仍由用户保留的未知项写入待确认，禁止伪装成定案。
4. 不写接口、文件、实例编号、代码结构或代理推测。开发拆分只在用户明确进入开发阶段后交给工作区自定义任务管理技能。

用户要求立即输出草案时可以整理，但标题和回执必须说明“策划草案，仍有待确认项”，不得标记策划完成。

## 停止条件

- 用户明确暂停、取消或只要求讨论时停止写入。
- 玩法选择取决于尚未查明的平台能力时，说明缺口并转入能力查证，不靠假设继续。
- 只有用户确认共同理解和正式策划案后，策划任务才能进入“待开发”；只有用户确认完成后才能标记完成。
