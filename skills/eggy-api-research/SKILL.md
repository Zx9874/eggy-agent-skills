# 蛋仔接口研究

本技能解决“为什么目标效果没有出现”，不是围着代理最先想到的接口不断换写法。

## 任务域

- **地图模式**：交付修改直接落入地图运行 Lua。使用当前地图定义、对应官方资料和地图开发技能的接口查证。
- **工具模式**：交付修改落入编辑器插件、命令行封装、转换器、技能、自动化脚本或其他辅助工具源码。使用工具当前定义、命令帮助、协议或类型、对应官方资料和示例；不询问地图，不加载地图开发技能，不维护地图项目文档，也不进入试玩流程。
- **混合任务**：按调用点分别研究，工具侧结论和地图运行侧结论不能互相代替。

## 何时进入

- 官方资料能证明接口存在，却不能证明它适合用户目标。
- 调用首次报错、没有效果、只有部分效果，或作用到错误对象、用户、进程或运行端。
- 参数、对象、生命周期、组件配置或两端变量关系仍不明确。
- 下一步只剩“再换个参数试试”，但没有新的证据。

证据已经覆盖当前目标环境、调用方、对象和目标效果，并且本次没有失败时，返回原开发流程，不额外研究。

## 先重新定义问题

先写一句可观察目标：谁在什么条件下做什么，应该看到什么。

- 地图模式确认运行端、目标对象、生命周期、多人数据归属和效果接收者。
- 工具模式确认调用进程和语言、接口提供方、调用通道、目标对象、生命周期、输入输出、权限与错误返回。

失败原因至少从这些方向检查：

1. 接口能力选错，真正入口可能是组件、事件、命令、配置或通信协议。
2. 目标环境、调用阶段、进程或运行端不匹配。
3. 调用形式、接收对象、静态与实例方法不匹配。
4. 对象尚未加载、已经销毁、调用顺序或前置状态错误。
5. 参数数量、顺序、类型、单位、范围或变量来源错误。
6. 外部配置、资源结构、权限、绑定或连接信息不完整。
7. 状态所有者、返回接收者或跨进程数据关系错误。
8. 当前接口实现缺陷或官方资料未写明的边界。

## 候选与证据

从当前交付物可见的接口定义、对应官方资料和官方示例寻找候选。地图模式可用安装后的 `<总工作区>/.eggy-agent/scripts/api-preflight.ps1` 定位命中，再阅读上下文核对准确接口；必填参数为 `ProjectPath`（地图路径）、`ApiName`（接口名）和 `DocsRoot`（对应版本手册目录），可另传 `ExamplesRoot`（官方示例目录）。缺少资料先报告，不捏造路径。工具模式直接搜索工具代码、命令帮助、协议或类型定义，不运行地图专用查证脚本。

- 先排除接口不存在、目标环境或调用方不符、对象类型不符的路线。
- 优先验证官方语义最明确、对象最匹配、成本最低的候选。
- 没有第二个有证据候选时如实说明，不编造相似接口。
- 已被证据淘汰的路线，前提不变且没有新证据时不得重试。

## 最小实验

每个批次先列出当前卡点、仍成立的候选原因和证据将决定的下一步。一次只改变一个会影响因果判断的独立变量，但应在同一条件下集中观察能区分多条候选路线的相关状态，避免为每个小问题重复运行或试玩。先选择最便宜且不污染项目的方法：

1. 读取定义、配置、对象状态或本轮增量日志，不改代码。
2. 在当前正式调用点只改一个可回退的小范围参数、目标或时序，并只验证一个代表性用例。优先复用 Git 差异或临时标记完成回退，不为每次实验复制备份；该改动不得影响无关功能，也不得未经确认改变对外契约。
3. 复用项目已有测试入口或测试模块。
4. 在现有安全位置加入最少的临时测试代码。
5. 只有前四种都无法隔离，或实验失败可能阻断正式流程时，才新建一个独立测试文件和最多一处临时入口。

地图模式创建临时测试代码、测试日志或测试文件时必须加 `【测试专用】`，跨客户端和服务端的问题分开验证。工具模式遵守目标仓库已有测试命名和结构，不使用地图测试标记；只有临时代码会被注入地图运行工程时才加该标记。跨进程或跨协议问题分开验证。编辑器命令行可以执行已查证、单一目的的只读或可恢复检查，不得拼接大段代码同时改变多个变量。

测试工具自身的路径、编码或命令错误不算接口实验；先把最小工具链修通，不为这类手误写长期记录。

## 继续、停止与扩大

- 只有新证据能缩小候选范围、支持新的可区分路线或使旧证据失效时才继续取证。
- 无报错、命令成功或打印日志不等于效果通过；目标效果、对象和接收者必须正确。
- 结果无法区分原因时先改进观察方式，不继续换参数。
- 没有新证据、资料冲突、缺少用户配置或无法安全隔离时停止并说明阻塞。
- 结论通过后先保留一个正式调用点和一个代表性用例做试点；试点正确后才扩大，失败立即返回研究。

## 退出研究测试

证据足以选择接口路线、参数关系、作用对象或正式修复位置后，当前研究测试立即结束，不能一边写完整正式功能一边继续扩充测试工具。

- 通过：把已确认结论用于正式调用点，删除临时测试内容，返回编码流程。
- 失败且原因已确认：停止加观察点，返回编码流程修正式代码；修复后只有新的明确问题才重新研究。
- 无法区分：如果存在能直接区分剩余路线的低成本观察，可在当前批次补充；否则停止改文件并说明缺少的证据。
- 阻塞：停止改文件，说明缺少的配置、权限或用户操作。
- 等待用户执行已授权试玩或工具运行验证：只保留现有最小观察点并冻结相关文件，不追加测试代码。

重新进入必须有新的可区分路线、正式代码变化或证据来源，并说明上一轮证据为何不足。地图模式达到待试玩且没有未决卡点时标记“待试玩”；工具模式达到可运行验证状态时标记“待运行验证”。两种模式都不能为了未来可能的测试继续扩充研究代码。

## 记录

实验过程默认留在当前会话，不为每轮建立表格或文档。地图模式只有以下内容写入当前任务载体；若研究将跨会话或决定多个正式调用点，先由 `eggy-dev-plan` 建立独立任务文件。工具模式按目标仓库已有任务或文档约定记录，不创建地图开发计划：

- 需要跨会话继续的当前结论、已排除路线和下一步。
- 会改变正式实现方向的决定。
- 研究停止时仍未解决的阻塞。
- 批次结束时已经验证的参数关系、边界和适用范围。

写入时覆盖更新一段紧凑研究摘要，不追加每条命令和原始日志。经过验证、能跨地图复用且可避免高代价复发的结论，地图模式在收尾时交给 `eggy-kb`。工具模式按工具项目已有知识或文档约定保存，不要求加载地图知识技能或新建地图文档；普通失败和手误不沉淀。

向用户只报告目标效果是否出现、当前最可能原因、这轮改了多小的范围、排除了什么、是否可以扩大，以及仍需用户执行的最短操作。
