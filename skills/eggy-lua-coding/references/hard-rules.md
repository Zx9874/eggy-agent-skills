# 公开版 Lua 开发硬规则

以下规则适用于地图运行 Lua，工具开发不加载本文件。

## API

- 写代码前必须确认接口存在，并查完整签名、参数数量、顺序、类型、返回值、调用对象、运行端、默认值、范围和前提。
- 当前工程定义、对应版本官方手册和官方示例分别承担不同证据；三者不能互相替代。
- 资料冲突或缺少关键关系时保持未知，先研究或做最小实验，不连续改写法碰运气。

## 代码与文件

- 官方生成目录、数据映射、接口定义、工程配置和编辑器技能只读。
- 功能代码放自建模块，入口只做装配；同步到地图的 Lua 文件名使用英文、数字和连字符或下划线。
- 有准确资产编号时优先使用已确认编号；没有编号才按名称查询，并核对返回数量。
- 外部导出函数、事件名和可视化绑定名称默认冻结；任何改名、移动或签名变化先确认。

## 恢复依据与批量修改

- 代码、文档和规则文件先记录已有 Git `HEAD`（当前提交）及未提交差异；这已经是恢复依据，不得为了“建立恢复点”再复制文件、创建备份分支或重复提交。
- 只有 Git 无法完整恢复的编辑器场景、UI（界面）、预设状态，或用户明确要求时，才保存一次本批目标范围快照。后续操作复用同一快照，不按文件、函数、节点、参数或每轮实验重复备份，也不复制整张地图。
- 批量修改仍须先试点、精确匹配、排除官方文件和他人改动，并逐文件审查差异；恢复依据规则不改变这些安全要求。

## 测试与沟通

- 没有用户要求不得启动编辑器或试玩。
- 测试以打通当前卡点为目标，先做最小可回退试点；优先复用 Git 差异和现有测试位置，不为每次实验复制备份。临时代码和日志标记 `【测试专用】`，证据足够后清理并退出测试模式。
- 正常流程用调试日志，真实异常用警告，已失败用错误；日志优先中文且避免高频刷屏。
- 报错先用大白话解释原因和影响，再按授权修复。用户未确认的功能不能写成完成。

## 注释与文档

- 每个新增或修改函数说明用途；复杂逻辑补充输入、输出、副作用、失败条件、清理时机和顺序依赖。
- 用户明确说明的修改原因写在附近注释，不伪造用户原因。开发日志只留批次效果、关键原因和验证状态，完整代码历史由 Git 保存，不把聊天或命令流水塞进代码和文档。
- 每张地图维护一个需求文档、开发计划、资产清单、项目总览和开发日志。跨地图复用知识只有经过证据确认后才进入可靠知识库。
